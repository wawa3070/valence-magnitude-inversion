When the Story Doesn't Match the Math: Runtime Verification of LLM-Narrated SHAP Explanations

Seven workhorse-tier models · two domains · 85 loan generations + 50 real-TreeSHAP alerts per model

Production ML systems increasingly use LLMs to translate SHAP attributions into plain-English explanations for applicants, operators, and auditors. That translation step is unchecked: the sentence sounds like the math, but nothing forces it to match the math. This project documents a silent failure mode — valence–magnitude inversion: the narrative orders features by tone (good news first) instead of importance, so every stated fact is correct while the ranking is wrong — invisible to checks that only test factuality. Because the ground-truth SHAP vector is known at generation time, faithfulness can be verified automatically and nearly for free.

The failure mode

Ask an LLM to turn a SHAP vector into a customer-facing sentence and it will oblige, fluently:

“The primary driver for your approval is your excellent Credit Score. Your Annual Income also played a positive role, though your high Debt Ratio slightly decreased your score.”

Every fact is correct. But the attributions were (Credit Score +0.45, Annual Income +0.25, Debt Ratio −0.35): by magnitude, Debt Ratio outranks Annual Income. The model ordered features by valence — good news first — not by importance. A reader who trusts the order of the prose walks away with the wrong causal picture, and no factuality-based detector fires, because nothing was fabricated.

Formally: let ϕ ∈ Rd be the SHAP values for one prediction and let π* rank features by |ϕj| descending. A narrative induces its own ranking π̂, operationalized as first-mention order. Inversion occurs when π̂ ≠ π*. Valence–magnitude inversion is the specific, directional case where π̂ sorts positive contributions ahead of larger-magnitude negative ones — systematic rather than random, driven by the politeness conventions of instruction-tuned models, and consequential wherever stated priority matters: adverse-action notices, incident triage, model-risk reviews.

What is a trap?

A trap = an alert (or instance) where tone-ordering — positives first, then negatives by ascending magnitude — produces a different feature order than true importance-ranking by |SHAP|. Only traps can reveal inversion: when the two orders coincide, a tone-driven narrative is indistinguishable from a faithful one, which is why both experiments select trap instances deliberately.

Worked example

Three features, one SHAP vector, two orders.

Tone ordering (good news first)

Positive SHAP values, descending:

  • Feature_A+0.6
  • Feature_C+0.1

Negative SHAP values, absolute ascending:

  • Feature_B−0.5 (absolute 0.5)

Tone order: ['Feature_A', 'Feature_C', 'Feature_B']

Magnitude ranking (true importance)

By |SHAP|, descending:

  • Feature_A+0.6 |0.6| → rank 1
  • Feature_B−0.5 |0.5| → rank 2
  • Feature_C+0.1 |0.1| → rank 3

Magnitude order: ['Feature_A', 'Feature_B', 'Feature_C']

▲ Is trap? Yes — the two orders differ, so a narrative that leads with the good news demotes Feature_B from second to last.

def tone_ordering(features, shap_vals):
    """'Good news first': positives by value descending, then negatives by |value| ascending."""
    pos = sorted([i for i, s in enumerate(shap_vals) if s > 0], key=lambda i: -shap_vals[i])
    neg = sorted([i for i, s in enumerate(shap_vals) if s <= 0], key=lambda i: abs(shap_vals[i]))

The runtime contract

Rank check (confident wrongness)

Extract π̂ from the narrative — first-mention order over a known feature vocabulary, nothing beyond pattern matching — and compute Spearman's ρ(π̂, π*) over the mentioned features. Unmentioned features count against a coverage requirement. One regex pass and one statistic per output; it doubles as the regression test for any prompt or model change.

Fallback ladder (no human rater)

Flagged narratives descend: regenerate once → templated explanation (always faithful, merely uglier) → raw attribution table. The gate changes what the existing operator sees, not who exists. Where token logprobs are available, an uncertainty tripwire on generation entropy can be layered on top — proposed, not evaluated here.

How a narrative is scored

The harness extracts the feature order by first mention in the generated text (unmentioned features are dropped; fewer than three mentions is incomplete and unscoreable), then compares that order with the true ranking:

rho
Spearman's rank correlation coefficient, measuring how well the narrative's order matches the true magnitude ranking. ρ = 1 is a perfect match; ρ ≈ 0 means prose order carries essentially no information about importance.
faithful_order
A boolean indicating if the narrative's order perfectly matches the magnitude ranking.
tone_ordered
A boolean indicating if the narrative's order perfectly matches the tone_ordering (and is not faithful_order), signifying a potential 'inversion' bias.

Aggregated per model × condition as mean ρ, strict % inverted (= 100 − % faithful), % tone-ordered on traps, coverage, and — for local models — mean token entropy.

Experimental setup

Why the “workhorse” tier. Narrating an attribution is a per-decision, hot-path task: in deployment it runs once for every loan adjudicated or every alert raised — potentially millions of calls a day — under tight latency and unit-cost budgets. Those economics rule out flagship reasoning models for the narration step and select exactly the tier studied here: each vendor's light, fast, cost-efficient offering (Gemini 3.6 Flash, Claude Haiku 4.5, GPT-5.6 Luna, GLM-5.2, Kimi K3, Qwen 3.7 Max) plus a small open-weight model (SmolLM3-3B) standing in for data-sensitive finance and SOC settings that cannot ship records to a hosted API. The failure rates below are the ones a real deployment of this pattern would encounter.

Headline findings

  1. Unfaithful ordering is the baseline norm for every model. At C0, 52–76% of loan narratives mis-order features and mean ρ sits between −0.10 and 0.40 — prose order is essentially uninformative about importance.
  2. The strongest models fail most politely. The tone-ordered (good-news-first) share of trap narratives is highest for Kimi K3 (50%) and Gemini 3.6 Flash (42%) on loans, and for Gemini (54%) and Kimi (50%) on network alerts. A typical Kimi miss: for (Recent Inquiries −0.47, Credit Score +0.40, Loan Amount +0.24) it leads with “your strong credit score” and buries the larger negative inquiries last.
  3. Instruction-compliance splits the fleet three ways — and that is the point. Robust: Gemini 3.6 Flash, Kimi K3, Qwen 3.7 Max, GPT-5.6 Luna become faithful under the ordering instruction (C1 ρ = 1.00, 0% inverted) and stay faithful under competing warmth and six features. Partial: GLM-5.2 (ρ = 0.65, 22% still inverted at C1) and Claude Haiku 4.5 (ρ = 0.82, 20%) improve but degrade again under warmth (33% and 40%). None: SmolLM3-3B is unchanged (76% inverted at both C0 and C1). The split cuts across vendors and sizes and is invisible from outside.
  4. On real attributions, model identity dominates — and flips across domains. Baseline inversion on real per-alert TreeSHAP spans 0% (SmolLM3-3B, ρ = 1.00) to 86% (Qwen 3.7 Max), with no size or vendor pattern. The same SmolLM3-3B that is perfectly faithful there is 76% inverted on the loan vectors; Claude Haiku 4.5 shows the same flip (12% vs. 52%). Faithfulness is a property of the (model, domain, instance) triple, not of the model.

Discussion

Prompting is mitigation, and an unreliable one: the ordering instruction did nothing for SmolLM3-3B and only partly worked for GLM-5.2 and Claude Haiku 4.5, with warmth eroding both. Nor is faithfulness fixed within a model. Because the models under study are exactly the fast workhorse tier that per-decision narration deploys, these are the operative failure rates, not a worst case. A dependable system therefore needs to know whether this output is faithful — and the check costs one regex pass and one statistic per output.

Limitations. First-mention order proxies claimed importance; the loan vectors are synthetic (the network case study, by contrast, scores real per-alert TreeSHAP from a detector trained on synthetic SDN traffic); the uncertainty tripwire is proposed but not evaluated; and the stress conditions C1/C2 have so far been run on the loan domain only, with the network-domain replication in progress.

Reproducing

Open the notebook in Colab — it runs top-to-bottom on a free T4. The GPU is only needed for the local SmolLM3-3B rows; API models are optional (add OPENROUTER_API_KEY and/or GEMINI_API_KEY in Colab Secrets, and any model without a key is skipped with a note). Both CSVs load directly from the repo, so there is nothing to download and no Drive mount.
